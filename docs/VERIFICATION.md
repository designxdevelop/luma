## Govee Home sign-in, partner metadata, and DreamView draft

Sign-in follows two independent public clients that agree on the contract: homebridge-govee @ `c7b3037bddaf465e440276a8fe74c8ec4e42e13a` (`lib/connection/http.js`, `lib/utils/device-context.js`) and goveetl @ `3890402` (`internal/govee/auth.go`, `app.go`, `types.go`). `POST https://app2.govee.com/account/rest/account/v2/login` `{email,password,client[,code]}`; status 454 → `POST account/rest/account/v1/verification` `{email,type:8}` then login again with `code`; `GET bff-app/v1/device/list` with `Authorization: Bearer`. Headers are homebridge's set (`appVersion 7.4.10`, `clientType 1`, `iotVersion 0`, `timestamp`, `clientId`, iOS `User-Agent`). `clientId` is one random ID kept in the Keychain so Govee doesn't ask for a code on every sign-in. Redirects are refused (the body carries the password); server messages are never shown; the password and code live only in the sheet. The token goes to the Keychain with `tokenExpireTime` read as milliseconds (unit unverified: goveetl only stores it and homebridge ignores it); an expiry already past at sign-in is dropped so the server's 401/403 decides, which clears the session. Refresh (`bff-app/v2/account/refresh-token`) is only in goveetl with a different header set, so it isn't used. Demo mode can't sign in.

Parsing adds `deviceExt.deviceSettings` (a JSON-encoded string per homebridge; objects accepted too): `bleName`, `address`, and `versionSoft`. Bluetooth identity is in memory only; drafts are saved as optional `dreamViewDrafts` (homes saved earlier still decode). The earlier key-name scan for group fields was removed after the live read below found none.

DreamView draft: members and areas 1–10 (ha-govee-led-ble @ b845c59 wire values; positions on screen unverified) are stored locally. Member caps are shown only for SKUs ha-govee-led-ble lists (H6199 5, H6097 7, H6099 7, H66A0 10), otherwise "?". Apply is disabled with its reason.

## Siri, Shortcuts, and one-tap Govee scenes (2026-11-02)

**Siri / Shortcuts.** Six App Intents in a new `LumaIntents` module (shipped inside the `LumaUI` product, so the Xcode projects need no new package reference): Turn On Room, Turn Off Room, Set Room Brightness (1–100), Set Room Color (8 colors, 4 whites clamped to each light's range), Run Luma Scene, Apply Govee Scene. A room entity is the room's name (plus an **All lights** entry); the action looks up the room's members when it runs, so lights added to or moved out of a room after a shortcut was made are picked up. Lights reported offline, or lacking the control, are skipped and named in the reply; nothing sent → the action fails with that reason. Writes return once LAN or the cloud accepts them (readback continues in the app), so a room reply isn't held behind confirmation reads. Run Luma Scene waits up to 20 s for the scene's steps. A room shortcut whose room was renamed resolves to an empty room and says so. The App Shortcuts provider lives in each app target (`ios/Luma/LumaShortcuts.swift`, `macos/Luma/LumaShortcuts.swift`), with six shortcuts and two or three phrases each; the app calls `updateAppShortcutParameters()` at launch and whenever room or scene names change. Both apps share one `HomeStore.shared` between the window, the watch relay, and intents.

How it runs: intents execute in the Luma app process (no extension), which iOS launches in the background without a window when needed. That process reads the same `home.json` and Keychain items, so no App Group or Keychain access group is needed. Both are readable after the first unlock following a restart (`completeFileProtectionUntilFirstUserAuthentication`, `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`), not before. LAN addresses aren't saved, so a cold launch sends through the Govee cloud (the saved API key is required); LAN is used when Luma is already running and has found the light. On a cold launch, actions wait only until the cloud client exists, not for every light's state read.

Apple limits (sources: [WWDC22 session 10170](https://developer.apple.com/videos/play/wwdc2022/10170/) (phrases include the app name); Apple DTS answers in [forum 779109](https://developer.apple.com/forums/thread/779109) (one parameter per phrase), [777854](https://developer.apple.com/forums/thread/777854) (phrase parameters must be AppEntity/AppEnum, no free text), and [795383](https://developer.apple.com/forums/thread/795383) (10 App Shortcuts shown)): every phrase names Luma; a phrase holds one room or scene name, so Siri asks for the brightness, color, or Govee scene; Luma uses 6 of the 10 shortcuts. Apple's App Intents reference doesn't state a time limit for `perform()`; none is assumed beyond Luma's own 20 s scene wait. A scene with long waits may be suspended with the rest of the app once it returns. Luma sets no authentication policy; Lock Screen behavior was not tested.

**Govee scene browser.** `GoveeSceneLibrary` (LumaCore) lists a light's `lightScene`, `diyScene`, and `snapshot` options with Govee's names, in Govee's order, and a placeholder for unnamed options. The browser (Scenes › Govee scenes › Browse; each light's Effects tab) searches case- and accent-insensitively, filters by kind, and applies with one tap: one light gets its exact option; a room gets each light's option with the same kind and name, and lights without it are skipped and named. No Luma scene is created unless **Save as Luma Scene** is chosen. A DIY reload now replaces the DIY list (built-in lists still merge, since the device list and scene endpoint each carry part), and a saved scene pointing at a removed option fails validation with "… no longer lists this Govee scene". Scene lists stay the public API's per-model lists; Govee Home can show more. The demo lights now carry sample scene lists so the browser and Siri's Govee scene action can be tried without an account.
